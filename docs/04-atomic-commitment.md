# Atomic cross-shard commitment

This document covers the machinery that gives Hyperscale single-chain semantics across shards: a transaction touching state on several shards commits atomically — the same terminal outcome, on every participating shard, with BFT finality — or aborts everywhere. The protocol is a deterministic **provision–execute–certify** pipeline built from three ingredients: **declared state access** (the transaction says up front what it touches), **provisions** (QC-attested state transfer between shards), and **execution certificates** (per-shard quorum agreement on a shared outcome vector, described in [01-consensus-layers.md](01-consensus-layers.md) §2).

**If you know two-phase commit, read this first.** The family resemblance is real — ordering a transaction with its reservations held plays the role prepare plays classically — but the three defining features of 2PC are all absent. There is **no coordinator**: the protocol is symmetric across shards, so the coordinator-failure blocking problem that defines textbook 2PC has no analogue. There are **no votes on the outcome**: in 2PC the result is genuinely open until participants' votes are tallied, whereas here it is a deterministic function of committed chain content — which transactions ordered, and which provisions landed by the attested deadline. Execution certificates *attest* an outcome every honest replica already computed rather than *choosing* one. (The closer lineage is deterministic databases, where determinism replaces commit-time agreement, not distributed transactions.) And **participants don't fail in the 2PC sense**: each "participant" is a BFT-replicated committee, and even a participant shard ceasing to exist mid-flight — a case classical 2PC has no answer for — resolves deterministically: a departed shard's verdicts are read from the lines of its own terminal block ([02-dynamic-sharding.md](02-dynamic-sharding.md) §4).

Main code homes: `crates/mempool` (admission and availability), `crates/provisions` (provision coordination and DA), `crates/execution` (ticks, vote aggregation), `crates/engine` (the effect-typed engine and its fee rules), with the wire types in `crates/types` (`Provisions`, `ProvisionEntry`, `ExecutionCertificate`, `Finalization`).

## 1. Declared access and the mempool

Every transaction's declared access is derived from its signed envelope through the effect DSL — the set of keys it reads and writes, each carrying the owner prefix that places it. Declaration is the foundation of everything downstream: it determines routing (which shards participate — the shards those prefixes route to, via the shard trie), it bounds execution (a guest reaches a cell only through a capability the derivation granted, so an undeclared write is unreachable), and it enables contention analysis without executing.

The mempool (`MempoolCoordinator`) admits transactions into a hash-ordered pool with process-level dedup caches shared across co-hosted vnodes (`CanonicalTxs` — one signature/HBOR validation per transaction per process; `TxStatusCache` — one status truth for RPC). Terminal-state tombstones prevent re-admission of finished transactions.

**Admission does not arbitrate conflicts.** Selection is hash-ordered iteration over the eligible pool up to the block budget; two transactions touching one cell are both selectable. What sequences them is execution: a committed block's work is one batch, partitioned into conflict groups and run against a single overlay, and each batch's output is the next batch's baseline. Contenders therefore see each other's writes instead of being held apart, so a hot cell does not cost a commit cycle per transaction.

A count budget (`MAX_UNSETTLED_TXS`) bounds the drain a shard still owes — the member rows standing in its committed state, one for each transaction it has committed and not finished with. The total (`txs_in_flight`) is the number of those rows after the block's own fold, carried on the block header, so every replica reads the same number rather than one that drifts with its own pipeline position, and what it bounds is *adding* to the drain: a block bringing new transactions to a drain already over budget is invalid, while one carrying only certificates stays valid at any total. See [06-resource-economics.md](06-resource-economics.md) §5 for why the asymmetry is load-bearing.

**Authorization splits between admission and execution.** A VM manifest node names its target by address, and an address is public — naming one is evidence of nothing. Each method a package publishes declares whether reaching it requires an identity: `deposit` does not, because being paid is not a decision the recipient makes, while `withdraw` and the entropy stamp do, because spending an account's funds and writing its leaves are. A guarded node must present a claim, and an intent's own signature resolves to the claim on the account that intent acts as — so moving a second party's funds takes an intent that party's account signed, and an ordinary transfer still settles under the sender's single signature. That much reads only signed content and content-addressed package metadata, never state, so it sits beside the rest of derivation, ahead of ordering and ahead of any fee exposure: an envelope presenting nothing where something is required never enters a block and nobody pays for it (INV-VM-AUTH-1). Whether the keys behind that signature may act as the account is the account's own shard's question, judged against its stored rule at materialization before any body runs (INV-VM-AUTH-6). Whether the claim a call presents is the one its target requires is the target's own question, answered at execution against the target's state, and a call presenting anything else aborts with its sender paying the ceiling they signed (INV-VM-AUTH-2). Accessibility is a declaration the package makes about its own methods, carried in the metadata section its content address covers, so no transaction can weaken it and every shard reads the same one.

## 2. Provision: proven state transfer

When a source shard commits a block containing cross-shard transactions, its proposer broadcasts **`Provisions`** to each destination shard — one bundle per (source block, destination shard):

- Per transaction: the substate values the destination needs (`entries`, canonically sorted) and nothing else — a bundle carries state, never a claim about where state lives (§5).
- A JMT merkle **multiproof** over all carried substates against the source block's state root.

A bundle carries the **read set and nothing else**: fresh reads, and the prior values of read-modify-write keys. A blind write provisions nothing because the destination never needs what it is about to overwrite; an increment provisions nothing because it never reads the value it adds to; a reservation's feasibility is judged where the reserved substate lives. A leg whose dependency set is empty dispatches immediately rather than waiting on a bundle that would carry no state.

An empty bundle is still emitted, and that is a second job the same wire edge does. A counterpart engages a cross-shard transaction only against evidence that the shard paying its fee committed it, and that evidence is exactly the payer's bundle bound to its source block through the header's `provision_tx_roots`, consumable only against a commit-proven header (INV-VM-HOST-1). Every other participant echoes its own commitment back to the payer the same way, which is what lets the payer's single vote be a pure function of its own chain (INV-VM-HOST-3).

Verification at the destination is two-stage and entirely artifact-based. The source block's header is already held and QC-verified via remote-header sync ([03-state-and-sync.md](03-state-and-sync.md) §6), so verifying a provision bundle means one QC check per source block plus merkle verification of every entry against the attested state root. A provision is a *proof about a committed remote block* — no node in the source shard is trusted, only its quorum (INV-EXEC-10). Verified provisions are persisted and flow into tick composition.

**Value crosses as a record, not in a bundle.** Value one leg hands to a leg on another shard is a crossing record the producer's leg writes into its own state. The record reaches every committee that runs its consumer as a pushed, self-proving `StateClaim`, with a read at a commit-proven anchor as the fallback. An escrowed record is taken by the consumer's member; an owed one is credited by the consumer's commit fold. The consumer's answer, `Taken` or `Never`, is a cell under the consumer, and settlement is written in the commit folds: the producer retires a record whose `Taken` it reads and takes back one whose `Never` it reads at a boundary of the consumer's shard, or at its own parent where one chain holds both ends, crediting the cell its value left where that cell takes the return whole, and otherwise the principal vault of the record's owner, whose cell it left, and the consumer deletes an answer once it reads, at a boundary of the producer's shard, the record absent, and for a `Never` whose record it never read, the producer's member exited, or the record absent at its own parent where one chain holds both ends. That exit is the producer's member row read absent: at its finalization where the member ran, and, for a leg that never ran, at the fate that ends its row when its leg entry window closes. Until then the consumer keeps the answer and asks again at each boundary of the producer's shard.

**The header also pre-announces.** Source block headers carry per-destination `provision_tx_roots`, so a destination knows what to expect and can detect absence — absence of data, unlike presence, needs an announcement to be actionable. A verdict needs no such announcement: a stated member's row names the shards whose verdict it awaits, and reads each one's verdict leaf in that shard's committed state.

## 3. Execute and certify: outcome agreement by determinism

At the destination (and symmetrically on every participant), a committed cross-shard transaction joins a **tick** once its provisions complete: the block's tick manifest names it in a member line, and every replica folds the same member rows from the block, so which tick holds a transaction is committed content rather than each replica's own composition. The row is written by the block that commits the transaction, on the terms that block states for it — its reach, what it awaits, its abort charge, its share and its local reservations — and it carries them until it leaves. While it waits the row also carries what it waits on, the bundles it requires and the crossings it consumes, so the lines a later block names for it are read off the row alone. From its commit until its writes land, when the row is deleted or stands accepted, it also carries what it owes: how many of the escrowed crossings it consumes come from each producer route. A block that commits and runs a transaction states its terms entry only where those terms carry crossings, so the row its line writes owes them from that block too.
 Execution merges local snapshot state with the provisioned remote entries and hands the tick's whole batch to the kernel's batch executor at once.

Determinism across shards is engineered, not assumed:

- **Same inputs.** All participants execute from the same declared set and the same provisioned entries (QC-attested), under the same per-transaction environment: the clock is the payer shard's committing block's, locally available there and riding the payer's bundle everywhere else, and a random draw settles on the beacon's seed for the epoch that clock falls in, which every shard resolves identically.
- **Same engine, same outcomes.** The engine's output is projected to the executing shard (`CachedOutput`): a receipt hash covers only what that shard applies — its own slice of the writes, the events its own emitters produced, and the beacon-witness events lifted from them — so participants agree on the outcome, never on a shared receipt hash. All failures collapse to one canonical failed-receipt hash.
- **Same bounds.** A transaction can only write what its declared effects reach, so no execution-internal nondeterminism has a path into committed state (INV-EXEC-9).

Validators vote on the tick's `global_receipt_root`; 2f+1 matching votes form the shard's **ExecutionCertificate** with the explicit per-transaction outcome vector, each success outcome carrying its transaction's receipt hash. Every EC binds its root to its outcome vector (recompute-on-decode, INV-EXEC-2). Each shard's receipt hash covers only what that shard applies, so a quorum attests its own shard's content, and a certificate settles its own shard's members and decides nothing on another shard. A *core member*, one whose verdict other shards share, learns each sibling's verdict from that sibling's committed state, through a state claim its own chain carries. Abort is dominant; success is unanimous (INV-EXEC-1).

A `Finalization` — a certificate or names, with the receipts they settle — settles part of a tick. The determined half, the members awaiting no other shard, settles on the shard's own certificate and covers every row its tick holds for it: a block admits one only where its outcomes, each over a row, number the rows the tick holds in flight for that half, and refuses one over none, since the certificate projects to any part of its outcomes under one signature and a tick takes one determined half. The stating half says, once and whole, what that certificate reached for every member awaiting another shard, and carries no other certificate: a member it refused settles there on its refusal receipt, and a member it succeeded for is *stated* and settles nothing yet. A stated member's row stands on, holding what it held and recording the receipt hash the certificate attests for it, beside a `Yes` verdict leaf in the shard's committed state that names the transaction and the shards sharing the verdict; its share enters the block's fee total there, once.

A stated row *hears*: a block carrying a claim on a sibling's verdict leaf, or on its row and committed marker where the leaf is absent, records what the sibling's chain says on the row, the newest reading per sibling winning. One decision, evaluated alike by proposer and voter over the window the beacon published, reads those entries: an `Accepted` sibling accepts; else a sibling that left without accepting refuses; else a fresh `Yes` of every sibling accepts; else the row waits. A departed sibling is read from the `End` lines of its terminal block, and one past its evidence window is unreadable, which lets the row go. A **legs half** accepts stated members: it carries no certificate, names each member beside the receipt hash its row records, and carries the effects receipt that recomputes to it. A proposer cuts a legs half to the names whose decision accepts at its block's anchor; a voter refuses a name over a row that does not accept, and defers one whose window or names it does not hold. An accepted row holds and reserves nothing, its leaf reads `Accepted`, and it stands until every sibling has accepted, left or become unreadable, when an `End` line deletes it and its leaf. A refused stated row is aborted by a line, seated and settled off the line alone: its charge burns and the crossings it consumed are answered `Never`. Every line and legs half the decision licenses is optional: a proposer includes what its view licenses, and a block omitting one is voted, since no replica's view is owed to another.

Every half is judged against the rows its block's parent left, so a legs half rides a later block than its tick's stating half. A member whose siblings all said yes does not wait for a tick-mate whose sibling is slow or halted: a tick takes one stating half and as many legs halves as its members accept in, a block may carry several legs halves of one tick, and the tick owes a half while a member still stands in it. Determined halves settle in tick order along the header's `settled_tick_frontier`, and a stating or legs half settles only behind every determined half the chain owes at or below its tick: its members were judged over a baseline that already folds that output, so a debit of theirs never lands ahead of the credit it rests on. The member's provisional writes are promoted or dropped, its reservations release, and the transaction is terminal.

## 4. Aborts: deterministic, total, timely

Every path to abort is a pure function of committed chain state, so all replicas — and all shards — reach the same verdict:

- **Payer deadline.** A VM payer's own leg has no dependencies, so nothing outside the transaction gates it — and it must not run before it knows which verdict it owes, because the tick that runs it is the tick that attests it. It therefore joins a tick once every counterpart's engagement echo has committed on the payer's own chain, or once its signed validity window closes without them; in the second case the tick attests the all-abort carrying the fee record (INV-VM-HOST-3). Both conditions read only the payer's chain, so its committee cannot split into vote buckets, and a counterpart engaging at the window's edge resolves through abort dominance rather than as a verdict split.
- **Reshape-boundary aborts.** A core transaction toward a shard in its final epoch is not admitted, and one committed and still pending there is not run. When a participating shard terminates in a split/merge, the terminating chain's terminal block names an `End` line for every accepted row and a `Fate` line for every other member row it still holds, aborting each and burning its charge where its fee vault lies; a sibling still deciding reads the departed shard's verdict from those lines, a name among the `End` lines accepting and its absence refusing. The settled-set fence decides every abandonment record naming a straddler from frozen chain content ([02-dynamic-sharding.md](02-dynamic-sharding.md) §4). A fate is not the terminal's alone: on any block, a member a counterpart settles against whose every counterpart is unreadable is released by an `Unanswerable` discard of its tick and fated in the same manifest, or fated alone where a discard already released it. And the block anchored at the close of a member's leg entry window fates a leg no tick ever named and a released member settled on this shard's certificate alone: none is owed a certificate anywhere, and the fold's return of what a leg issued charges nothing, so the fate is the one burn of a leg that never ran. Voters expect exactly those lines, and the fold deletes the row, burns its charge and ends its fee hold in that block.
- **Abandonment.** A transaction the fence refused, or one whose batch no surviving execution state can finish, reaches no outcome by any path above. Each shard reads the transactions it has committed and not resolved from its committed member rows, and attests those past their own deadline — `validity_range` end plus `MAX_FINALIZATION_DELAY` — that no shard can still settle as `Aborted` in a later tick. A stated row is never among them: a row that said yes leaves only on what its siblings' state says, its chain's terminal, an unreadable sibling or its own recovery, and no deadline or record ends it. The abort is seated from its line alone, on a replica holding no execution state for the member as on one that does, and the settled-set fence asks nothing about it. The trigger is chain content on every replica, so the committee signs one verdict rather than each node reporting its own ([02-dynamic-sharding.md](02-dynamic-sharding.md) §4).
- **Halt recovery.** A shard whose committee halted is re-drawn by the beacon ([05-byzantine-safety.md](05-byzantine-safety.md) §1.4). Its crossing block, the first anchored at or past the recovery's bridge, discards every tick its parent's rows hold by a `Recovery` discard, so a tick the replaced committee certified stands only where a kept block settled it whole. No replica that has folded the recovery dispatches a run of a tick anchored below the bridge or signs one, and none runs a tick twice: the crossing raises the tick chain floor to its parent, and the first tick past it reads the base alone. A released member that ran and shares its verdict is aborted at once, stated or not, its consumed crossings answered `Never` unless a record covers it, and its verdict leaf goes with its row; one settled on this shard's word alone is fated at the close of its leg entry window, as any released member so settled is; one reaching no other shard is aborted at its deadline. An accepted row stands in no tick and is untouched. The recovered shard settles no half certified below the bridge in any block past it. What remains is a tear, a recorded outcome on both sides: a sibling that accepted on a yes the recovery discarded keeps its accept while the recovered shard aborts, and ends its accepted row on reading the abort, at most `MAX_STANDING_TOWARD_SHARD` members toward one shard (`shard_recovery.qnt`, `cross_shard_freeze`).

Abort is a first-class terminal outcome inside the EC's outcome vector — an aborted cross-shard transaction is *agreed aborted* with the same finality as a success.

## 5. Placement: a seam the key format closes

A substate key **is** its placement: the owner's prefix is the leading half of the key, so which shard owns a cell is a property of the cell's name. Remote-owned keys reach a participant only through provisions and local keys only through its own snapshot, so there is nothing to transfer, no precedence rule to arbitrate, and no contested claim to abort on.

That is worth stating as a closed seam rather than an absent feature, because the alternative was load-bearing and had a cost. Resolving ownership at execution time means a participant has to be *told* where a remote object lives, and a claim carried between shards has to be attested. Substate values prove into the QC-attested state root; a claim about ownership does not, and attesting one at transaction-hash granularity leaves a window in which a Byzantine source committee member's claims reach a destination's execution — contained to liveness only because every shard applies identical rules to identical bytes. Closing that by making the claim unnecessary beats attesting it, and it is the key format rather than any protocol machinery that does so.

## 6. Data availability

The DA design principle: **the artifact you need is either held by someone obligated to serve it, or provably expired.** Every retention decision keys on BFT-attested weighted time, so eviction is a consensus-consistent fact, not a local heuristic (INV-EXEC-7).

- **Outbound provisions** (`OutboundProvisionTracker`): a source shard retains what it broadcast until the destination's EC covers every transaction in the batch (a positive, quorum-signed acknowledgment) or the attested deadline passes. Until then, any destination node can fetch from any source node.
- **Serving fallback**: provision requests are answerable from committed storage — RocksDB plus historical JMT reads — bounded by the JMT retention window, so even a source node that restarted can serve.
- **Expected-transaction backfill** (`ExpectedTxs`): a destination that learns (from provisions) of transactions it never received by gossip fetches them from the source committee after a grace period, and abandons past the retention horizon.
- **Expected provisions**: symmetric tracking on the destination side, with fetch fallback when the gossip path fails.
- **Voting-time DA**: independent of all of the above, a validator votes only holding full block content, so every QC certifies 2f+1 complete copies of everything the block carries ([01-consensus-layers.md](01-consensus-layers.md) §1.2).

Fetch-path plumbing (one id-keyed `Fetch` state machine with a binding per payload, abandon-on-terminal notifications, class-based network prioritization so bulk DA traffic cannot starve consensus) is covered in [05-byzantine-safety.md](05-byzantine-safety.md) §6 and [07-determinism-and-testing.md](07-determinism-and-testing.md).

## 7. End-to-end walkthrough

A transaction declaring accounts on shards A and B:

1. **Admission.** Both shards admit it (routing by declared keys); a non-payer shard parks it until its payer's engagement evidence commits.
2. **Ordering.** A and B each commit it in a block, independently — there is no cross-shard coordination in consensus itself. Each commit writes the transaction's member row; its local writes stay provisional and its reservations hold until its tick's certificate resolves them.
3. **Provisioning.** A's proposer sends B a proven bundle of the substates B reads from A (and vice versa). Each side verifies against the other's QC-attested header.
4. **Execution.** Both sides hold the inputs they need; each executes its share and reaches the same outcome, with a receipt covering what it applies.
5. **Certification.** A's committee quorum-signs EC_A; B's signs EC_B. Each certificate settles its own shard.
6. **Stating.** Each side commits its tick's stating half on its own certificate. A side that refused the transaction settles its refusal there, and its row and leaf go; a side that succeeded states its yes, and its member row stands stated beside its `Yes` leaf.
7. **Hearing.** Each side's chain carries a claim on the other's verdict leaf, pushed by the block that wrote it or fetched by asking, and the stated row records what it says.
8. **Finalization.** On a `Yes` from the other side, each side commits a legs `Finalization` naming the member beside the receipt hash its row records, applies the effects receipt it carries and releases its reservations. Its row stands accepted until it reads the other side accepted too, and an `End` line deletes it. The transaction is terminal — identically — on both shards.

Any deviation lands in an exit both sides compute identically from committed state: the payer deadline, abandonment at the transaction's own deadline, a refusal read off the other side's exit, or — if one shard terminates in a reshape — its terminal's lines.
